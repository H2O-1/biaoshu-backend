# 招标解析逻辑问题与错别字识别功能拆分

> 目标：在现有“招标解析”模块基础上，新增逻辑问题识别和错别字识别。资格要求、评分标准继续复用现有建清单能力；法律风险和法律库本期暂不做。

## 1. 功能范围

### 1.1 本期要做

- 复用招标解析已有上传、INDEX、chunk 读取、任务进度、历史记录和详情能力。
- 文件索引成功后，读取本次招标文件的全部 chunk。
- 按批次将 chunk 文本交给 LLM 扫描。
- 每批输出逻辑问题候选和错别字候选。
- 后端对候选结果做合并、去重、排序和编号。
- 结果落库并在招标解析详情中返回。
- 每条逻辑问题、错别字都需要带 evidence，支持前端“查看原文片段”。

### 1.2 本期不做

- 不做法律风险识别。
- 不做法律库。
- 不改一键审查流程。
- 不改变资格要求、评分标准抽取链路。
- 不做复杂兜底；LLM 返回格式异常时，任务直接失败，便于早期调试。
- 不做人工复核工作流。
- 不做错别字自动替换，只给出识别结果和修改建议。

## 2. 推荐业务流程

1. 用户创建招标解析任务，上传一个或多个招标文件。
2. 后端沿用现有流程创建内部招标包、上传文件、创建 INDEX 子任务。
3. 文件全部 `INDEX_SUCCESS` 后，进入 `TENDER_ANALYSIS` 任务。
4. 任务执行：
   - 基础信息抽取。
   - 资格要求、评分标准抽取，继续复用现有建清单能力。
   - 读取本次文档全部 chunk。
   - 按批次扫描逻辑问题和错别字。
   - 合并候选结果。
   - 保存最终结构化结果。
5. 前端通过现有 job 轮询或 SSE 展示进度。
6. 任务成功后，详情页展示：
   - 基础信息
   - 项目简介 / 项目背景 / 项目概况
   - 资格要求
   - 评分标准
   - 逻辑问题
   - 错别字识别

## 3. 已确认产品规则

- 法律风险暂不做。
- 法律库暂不做。
- 逻辑问题和错别字识别使用全文 chunk 分批扫描。
- 资格要求和评分标准保持现状，继续复用 `ChecklistBuildPipeline`。
- 逻辑问题编号建议使用 `逻辑问题-1` / `逻辑问题-2`。
- 错别字编号建议使用 `错别字-1` / `错别字-2`。
- 每条结果都要支持查看原文片段。
- 每完成一项开发，需要同步更新本拆分文档和 `docs/API-招标解析.md`。

## 5. 数据模型建议

### 5.1 继续复用 `biz_tender_analysis_item`

本期优先复用已有条目表，不新增独立表。

新增 `item_type` 约定字符串：

| item_type | 说明 |
|-----------|------|
| `LOGIC_ISSUE` | 逻辑问题 |
| `TYPO` | 错别字识别 |

字段使用建议：

| 字段 | 逻辑问题 | 错别字 |
|------|----------|--------|
| `requirement_code` | `逻辑问题-1` | `错别字-1` |
| `title` | 问题标题 | 疑似错别字标题 |
| `content` | 问题说明 | 错别字说明 |
| `sub_type` | 问题类型 | 可空或错别字类型 |
| `source_excerpt` | 原文摘录 | 原文上下文 |
| `page_no` | 首个证据页码 | 首个证据页码 |
| `chunk_ids_json` | 来源 chunk id 数组 | 来源 chunk id 数组 |
| `evidence_json` | 证据数组 | 证据数组 |
| `sort_order` | 排序 | 排序 |

### 5.2 是否需要新增字段

本期先不新增字段，避免数据库扩展过重。

额外信息统一放入 `evidence_json` 或 `content`：

- 逻辑问题：
  - 严重程度
  - 问题类型
  - 修改建议
- 错别字：
  - 错误文本
  - 建议文本
  - 置信度
  - 修改建议

如果后续前端需要强结构化筛选，再考虑新增：

- `severity`
- `suggestion`
- `wrong_text`
- `suggested_text`
- `confidence`

## 6. 批次扫描策略

### 6.1 输入

批次扫描输入为若干个 chunk 文本。

建议每批包含：

- `chunkId`
- `documentId`
- `fileName`
- `pageNo`
- `chunkIndex`
- `content`

示例：

```text
—— 候选 1 ——
chunkId=101 pageNo=1 documentId=7 fileName=招标文件.pdf
预算金额为人民币 1280 万元。

—— 候选 2 ——
chunkId=104 pageNo=5 documentId=7 fileName=招标文件.pdf
投标人近三年需具有 5000 万元以上类似项目业绩。
```

### 6.2 批次 LLM 输出

批次输出是候选结果，不直接作为最终展示结果。

```json
{
  "logicIssues": [
    {
      "title": "业绩门槛与项目预算规模不匹配",
      "severity": "MEDIUM",
      "issueType": "THRESHOLD_INCONSISTENCY",
      "problem": "项目预算金额为1280万元，但类似业绩要求达到5000万元，门槛明显高于项目规模。",
      "suggestion": "建议补充设置依据，或调整为与项目规模相称的合理区间。",
      "evidence": [
        {
          "chunkId": 101,
          "pageNo": 1,
          "quote": "预算金额为人民币 1280 万元"
        },
        {
          "chunkId": 104,
          "pageNo": 5,
          "quote": "近三年需具有 5000 万元以上类似项目业绩"
        }
      ]
    }
  ],
  "typos": [
    {
      "wrongText": "解折",
      "suggestedText": "解析",
      "context": "解折失败，请重新解析",
      "confidence": "HIGH",
      "suggestion": "建议改为“解析”。",
      "evidence": [
        {
          "chunkId": 105,
          "pageNo": 6,
          "quote": "解折失败，请重新解析"
        }
      ]
    }
  ]
}
```

### 6.3 合并后结果

合并后结果是最终落库和接口返回的数据。

后端处理：

- 同类问题去重。
- 合并多个 evidence。
- 过滤无 evidence 的候选。
- 过滤低置信度错别字。
- 按页码、chunk 顺序排序。
- 重新生成编号。

最终落库示例：

```json
{
  "itemType": "LOGIC_ISSUE",
  "requirementCode": "逻辑问题-1",
  "title": "业绩门槛与项目预算规模不匹配",
  "content": "项目预算金额为1280万元，但类似业绩要求达到5000万元，门槛明显高于项目规模。建议补充设置依据，或调整为与项目规模相称的合理区间。",
  "sourceExcerpt": "预算金额为人民币 1280 万元；近三年需具有 5000 万元以上类似项目业绩",
  "pageNo": 5,
  "chunkIdsJson": "[101,104]",
  "evidenceJson": "[...]",
  "sortOrder": 1
}
```

## 7. Pipeline 拆分

### 7.1 `TenderIssueScanPipeline`

职责：

- 接收本次文档 chunk。
- 按批次组装 LLM 输入。
- 调用 LLM 扫描逻辑问题和错别字。
- 解析批次候选结果。
- 合并去重。
- 输出 `TenderAnalysisPort.ItemDraft` 列表。

建议方法：

```java
List<TenderAnalysisPort.ItemDraft> scan(List<DocumentIndexStorePort.ChunkView> chunks)
```

### 7.2 `LlmPort.scanTenderIssues`

职责：

- 输入一批 chunk 文本。
- 输出逻辑问题候选和错别字候选。

建议方法：

```java
TenderIssueScanResult scanTenderIssues(String chunksText)
```

### 7.3 `TenderAnalysisJobExecutor`

接入点：

```text
基础信息抽取
-> 资格/评分抽取
-> 逻辑问题/错别字扫描
-> 保存所有条目
-> markSuccess
```

## 8. LLM 提示词原则

- 只根据输入 chunk 判断，不允许引用外部法律法规。
- 不输出法律风险。
- 不猜测没有 evidence 的问题。
- 逻辑问题重点识别：
  - 同一文件内部金额、时间、数量、比例、门槛不一致。
  - 前后条款互相矛盾。
  - 评分总分与分项加总不一致。
  - 投标截止时间、开标时间、保证金截止时间明显冲突。
  - 同一术语、项目名称、文件名称前后不一致。
- 错别字重点识别：
  - 明显中文错别字。
  - 明显术语错误。
  - 明显多字、漏字、重复字。
- 不把专有名词、单位名称、项目名称轻易判为错别字。
- 不把 OCR 可能造成的断行、空格、页眉页脚当成错别字。
- 没发现问题时返回空数组。

## 9. 任务进度建议

沿用 `TENDER_ANALYSIS` 任务类型。

建议调整进度：

| progress | message |
|----------|---------|
| 10 | 文件解析中 |
| 45 | 基础信息抽取中 |
| 65 | 资格要求和评分标准抽取中 |
| 80 | 逻辑问题和错别字识别中 |
| 90 | 结果保存中 |
| 100 | 解析完成 |

## 10. API 变更建议

`GET /api/tender-analyses/{analysisId}` 详情新增：

```json
{
  "logicIssueItems": [],
  "typoItems": []
}
```

条目字段继续复用现有 `AnalysisItemDto`。

前端展示：

- 逻辑问题 tab 数量来自 `logicIssueItems.length`。
- 错别字识别 tab 数量来自 `typoItems.length`。
- “查看原文片段”继续使用每条 `evidence`。

## 12. 工作量评估

整体属于中等改造。

- 数据库：轻量，优先不新增表字段。
- Controller / API：较容易。
- LLM Port：中等，需要定义稳定 JSON 出参。
- Pipeline：中等，需要批次切分、候选合并、编号。
- 测试：中等，需要覆盖空结果、重复结果、格式异常、主流程落库。
- 主要风险：准确率、误报率、token 成本。
