# 招标解析模块功能拆分

> 目标：新增一个独立的“招标文件 AI 解析”模块。用户只上传一个或多个招标文件，不创建项目、不上传投标文件、不发起审查；后端解析招标文件并输出基础信息、资格要求、评分标准等结构化结果。

## 1. 功能范围

### 1.1 本期要做

- 上传一个或多个招标文件，形成一次“招标解析任务”。
- 自动执行文件解析 / 切块 / 向量化。
- 抽取招标基础信息：
  - 招标人
  - 招标代理
  - 预算金额
  - 投标截止时间
  - 项目简介
  - 项目背景
  - 项目概况
- 抽取资格要求。
- 抽取评分标准。
- 返回解析详情，用于前端结果页展示。
- 支持历史记录列表。
- 支持任务进度查询，优先复用现有 `biz_job` 轮询 / SSE 能力。

### 1.2 本期不做

- 不做投标文件审查。
- 不做投标包管理。
- 不做法律风险识别。
- 不做逻辑问题识别。
- 不做错别字识别。
- 不做 OCR；扫描版 PDF 若无法抽取文本，沿用现有失败逻辑。

## 2. 推荐业务流程

1. 用户进入“招标解析”页面。
2. 用户填写可选任务名称，上传一个或多个招标文件。
3. 后端创建一个独立招标解析记录，并为上传文件创建内部招标包（落 `biz_package`）。
4. 后端为文件创建 `INDEX` 子任务。
5. 文件全部索引成功后，发起 `TENDER_ANALYSIS` 解析任务。
6. 解析任务执行：
   - 基础信息抽取。
   - 资格要求抽取。
   - 评分标准抽取。
   - 保存结构化结果。
7. 前端通过 job 轮询或 SSE 展示进度。
8. 任务成功后进入解析详情页。

## 3. 已确认产品规则

- 解析任务需要落一个内部 `biz_package`，包类型沿用 `TENDER`。
- 任务名称为可选；不填时默认取第一个上传文件的文件名。
- `预算金额` 不拆分为预算金额 / 最高限价，本期统一存一个预算金额字段。
- `投标截止时间` 需要同时保存原文和标准时间字段。
- 前端需要“查看原文片段”按钮，后端结果需要返回可定位的 evidence。
- 资格要求和评分标准沿用现有 `Q1` / `S1` 编号。
- 历史记录删除先做逻辑删除：仅将解析记录标记为 `OBSOLETE`，不连带删除源文件、内部包和索引产物。
- 创建解析时前端必须为每个上传文件传 `fileType`；多文件按 `files[i]` 对应 `fileTypes[i]` 保存到 `biz_document.file_type`。

## 4. 复用现有能力

### 4.1 可直接复用

- `DocumentAppService` 上传校验和对象存储能力。
- `IndexJobExecutor` 文件文本抽取、切块、embedding、chunk/vector 落库能力。
- `JobPort` / `JdbcJobRepository` 异步任务表和任务状态流转。
- `JobController` 的任务查询和 SSE 能力。
- `DocumentTextExtractPort` PDF/Word 文本抽取。
- `ChunkingPort` 章节切块。
- `EmbeddingPort` 向量化。
- `RerankPort` 重排。
- `LlmPort` 的资格要求、评分标准抽取思路。

### 4.2 需要小改或抽象复用

- `ChecklistBuildPipeline` 当前绑定项目和清单表，本模块需要抽出“从招标文件 chunk 抽取资格/评分条目”的公共能力。
- `VectorRecallPort` 当前核心查询按 `orgId + projectId`，独立解析任务可能没有 `projectId`，需要支持按 `packageIds/documentIds` 召回。
- `DocumentAppService.upload` 当前依赖已有标包入口，本模块可能需要一个内部创建招标包并上传文件的专用入口。

### 4.3 需要新增

- 招标解析主表。
- 招标解析条目表。
- 基础信息抽取 prompt 和解析方法。
- 招标解析应用服务。
- 招标解析任务执行器。
- 招标解析 Controller。
- 招标解析 API 文档：`docs/API-招标解析.md`。
- 单元测试 / 流程测试。

## 5. 数据模型建议

### 5.1 主表：`biz_tender_analysis`

建议字段：

| 字段 | 说明 |
|------|------|
| `id` | 主键 |
| `org_id` | 所属组织 |
| `package_id` | 本次解析使用的内部招标包 |
| `name` | 任务名称；可空时默认取第一个上传文件的文件名 |
| `status` | `BUILDING` / `SUCCESS` / `FAILED` / `OBSOLETE` |
| `job_id` | 对应解析任务 id |
| `document_ids_json` | 参与解析的文档 ID 数组 |
| `tenderer` | 招标人 |
| `agency` | 招标代理 |
| `budget_amount_text` | 预算金额原文 |
| `bid_deadline_text` | 投标截止时间原文 |
| `bid_deadline_at` | 标准时间字段；无法可靠解析时可空 |
| `project_intro` | 项目简介 |
| `project_background` | 项目背景 |
| `project_overview` | 项目概况 |
| `evidence_json` | 基础字段证据，用于前端查看原文片段 |
| `basic_info_raw_json` | 基础信息 LLM 原始输出 |
| `checklist_raw_json` | 资格/评分 LLM 原始输出 |
| `error_message` | 失败原因 |
| `created_by` | 创建人 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

### 5.2 条目表：`biz_tender_analysis_item`

建议复用 `biz_requirement_item` 的核心结构：

| 字段 | 说明 |
|------|------|
| `id` | 主键 |
| `analysis_id` | 招标解析主表 id |
| `item_type` | `QUALIFICATION` / `SCORING` |
| `requirement_code` | 展示编号，如 `Q1` / `S1` |
| `title` | 条目标题 |
| `content` | 条目正文 |
| `sub_type` | 子类型 |
| `source_excerpt` | 招标侧原文摘录 |
| `page_no` | 页码 |
| `chunk_ids_json` | 来源 chunk id 数组 |
| `evidence_json` | 原文证据数组，用于前端查看原文片段 |
| `score_total` | 评分项满分 |
| `score_parts_json` | 评分分项 |
| `score_sum_matches` | 分值合计是否匹配 |
| `sort_order` | 排序 |
| `created_at` | 创建时间 |

## 6. 接口建议

### 6.1 创建解析任务

`POST /api/tender-analyses`

`Content-Type: multipart/form-data`

参数：

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 否 | 任务名称；不填则默认取第一个上传文件的文件名 |
| `files` | 是 | 一个或多个招标文件 |
| `fileTypes` | 是 | 每个文件的业务类型；与 `files` 按下标一一对应 |

返回：

```json
{
  "analysisId": 1,
  "jobId": 101,
  "packageId": 50,
  "documentIds": [7, 8]
}
```

### 6.2 历史记录

`GET /api/tender-analyses?page=1&size=20&keyword=`

返回字段建议：

- `id`
- `name`
- `status`
- `jobId`
- `fileCount`
- `createdAt`
- `updatedAt`
- `errorMessage`

### 6.3 详情

`GET /api/tender-analyses/{analysisId}`

返回结构建议：

```json
{
  "id": 1,
  "name": "智慧园区一体化平台建设项目",
  "status": "SUCCESS",
  "jobId": 101,
  "basicInfo": {
    "tenderer": "上海智慧园区发展有限公司",
    "agency": "中建咨询（招标代理）",
    "budgetAmountText": "￥12,800,000.00（含税最高限价）",
    "bidDeadlineText": "2026-08-15 17:00",
    "bidDeadlineAt": "2026-08-15T09:00:00Z",
    "projectIntro": "...",
    "projectBackground": "...",
    "projectOverview": "..."
  },
  "qualificationItems": [],
  "scoringItems": [],
  "evidence": [],
  "documents": []
}
```

### 6.4 删除记录

`DELETE /api/tender-analyses/{analysisId}`

本期删除策略：逻辑删除解析记录，仅将主表状态标记为 `OBSOLETE`；不删除该解析任务内部包、源文件、chunk/vector。

## 7. 任务类型建议

新增 `biz_job.type`：

- `TENDER_ANALYSIS`

任务状态沿用：

- `PENDING`
- `RUNNING`
- `SUCCESS`
- `FAILED`
- `CANCELLED`

建议进度：

| progress | message |
|----------|---------|
| 0 | 等待解析 |
| 10 | 文件解析中 |
| 35 | 文件解析完成 |
| 45 | 基础信息抽取中 |
| 65 | 资格要求抽取中 |
| 80 | 评分标准抽取中 |
| 90 | 结果保存中 |
| 100 | 解析完成 |

## 8. Pipeline 拆分

### 8.1 `TenderAnalysisAppService`

职责：

- 创建解析任务。
- 创建内部招标包。
- 上传文件。
- 创建 INDEX 子任务。
- 创建 `TENDER_ANALYSIS` 任务。
- 查询列表 / 详情 / 删除。

### 8.2 `TenderAnalysisJobExecutor`

职责：

- 认领 `TENDER_ANALYSIS` 任务。
- 等待 / 检查全部文件 `indexStatus=SUCCESS`。
- 有文件失败则整体失败。
- 调用解析 pipeline。
- 写入解析结果。
- 回写 job 状态。

### 8.3 `TenderAnalysisPipeline`

职责：

- 根据文档 chunk 抽取基础信息。
- 复用或调用公共要求抽取组件，生成资格要求和评分标准。
- 组装最终结果。

### 8.4 `TenderRequirementExtractPipeline`

建议从现有 `ChecklistBuildPipeline` 中抽出公共能力：

- 多 query 召回。
- BM25 + 向量混合召回。
- RRF 融合。
- 重排。
- 资格要求抽取。
- 评分标准抽取。
- evidence 生成。

现有建清单和新招标解析都调用这个公共组件。

## 9. 基础信息抽取策略

基础字段不建议只靠正则，建议“召回 + LLM 结构化抽取”：

1. 准备固定检索词：
   - 招标人
   - 招标代理机构
   - 预算金额
   - 投标截止时间 / 开标时间 / 递交截止时间
   - 项目简介
   - 项目背景
   - 项目概况
2. 在本次招标文件范围内召回相关 chunk。
3. 重排后把候选原文交给 LLM。
4. LLM 返回固定 JSON。
5. 后端做字段清洗和兜底校验；投标截止时间尽量解析为标准时间字段。

建议 LLM 输出包含证据：

```json
{
  "tenderer": { "value": "", "quote": "", "chunkId": 1, "pageNo": 1 },
  "agency": { "value": "", "quote": "", "chunkId": 1, "pageNo": 1 },
  "budgetAmount": { "value": "", "quote": "", "chunkId": 1, "pageNo": 1 },
  "bidDeadline": { "value": "", "quote": "", "chunkId": 1, "pageNo": 1 },
  "projectIntro": { "value": "", "quote": "", "chunkId": 1, "pageNo": 1 },
  "projectBackground": { "value": "", "quote": "", "chunkId": 1, "pageNo": 1 },
  "projectOverview": { "value": "", "quote": "", "chunkId": 1, "pageNo": 1 }
}
```

## 10. 权限规则

- 仅 `TENDERER` 可创建和查看本组织招标解析记录。
- 平台管理员无 `TENDERER` 角色时不可访问。
- 解析记录按 `org_id` 隔离，跨组织返回 `40400`。
- 删除 / 下载 / 预览也必须校验同组织归属。

## 14. 工作量评估

整体属于可控开发，主要风险不在工程结构，而在抽取准确率和字段定义。

- 后端骨架：较容易。
- 上传 / INDEX 复用：较容易。
- 基础信息抽取：中等，需要 prompt 和样例调优。
- 资格/评分复用：中等，需要从现有建清单流程中抽公共组件。
- 前端结果页数据结构：较清晰。
- 后续法律风险 / 逻辑问题 / 错别字识别：建议作为第二期扩展。
- 逻辑问题 / 错别字识别二期拆分见：`docs/招标解析逻辑问题与错别字识别功能拆分.md`。
